# Operating System Baseline — Paul

- **Version name:** Paul
- **Activation date:** 2026-09-20
- **Generation:** Rule-Minimal / Skill-Optimized
- **Status:** activation baseline
- **Predecessor:** Calvin
- **Canonical owner:** `HyungseonSong-plasma/chatgpt-operation`

## 1. Architectural objective

Paul changes the optimization surface from rule-working-set tuning to minimal rules plus deterministic skill delegation.

```text
Calvin
  -> optimize which prompt-visible rules are active

Paul
  -> keep only irreducible authority/semantic/claim-boundary rules
  -> delegate reusable deterministic procedure to tested/versioned skills
  -> activate skills only when their trigger applies
```

## 2. Essential rule layer

Paul's central prompt-visible common rule layer is:

```text
docs/operating_system/ESSENTIAL_RULES.md
```

It contains nine cross-repository invariants covering durable authority, exact pinning, read-only fail-closed init, semantic ownership, fresh evidence, evidence-class boundaries, real gates, durable resume, and documentation truth.

Consumer-specific semantic/scientific rules remain local.

## 3. Skill layer at activation

The central reusable skill set at Paul activation includes:

```text
session-bootstrap
state-refresh
repository-mutation
governed-work
controller-throughput
controller-lifecycle
```

A consumer is not required to load every skill simultaneously. Skill activation is trigger-based.

## 4. Common-rule extraction

The activation analysis is preserved at:

```text
docs/operating_system/COMMON_RULE_EXTRACTION.md
```

The extraction distinguishes:

```text
essential common invariant
deterministic skill mechanic
consumer-local semantic rule
```

This classification is the basis for future Paul rule minimization.

## 5. Operating metrics retirement

Calvin-era operating metrics were useful while the optimization target was rule loading/application and interaction-efficiency tuning.

Paul retires those metrics as active OS controls.

The following are not required for Paul initialization, routing, acceptance, or future OS operation:

```text
weighted rule-load score
rule-load GREEN/YELLOW/RED thresholds
WCC / T-WCC / RVR / EVR / DBR / RWR / CLR / FBR
rule-activation effectiveness scores
incident-rate percentages used as rule-quality scores
mandatory metrics context during bootstrap
```

Historical records remain preserved as archival evidence of the Calvin period.

Scientific, numerical, runtime, and performance metrics owned by consumer-domain validation are unaffected.

## 6. Consumer adoption contract

A consumer adopts Paul only through an explicit exact-revision binding update.

Paul initialization then follows:

```text
exact central revision
-> Paul registry
-> Paul essential rules
-> session-bootstrap + required init skills
-> consumer-local semantic authority
-> current durable state/evidence
-> first real gate
```

A consumer may remain on an older Calvin-pinned central revision until its binding is explicitly migrated.

## 7. Success criteria

Paul does not define success by minimizing a numeric rule count or maximizing a skill count.

The architectural success condition is qualitative and testable at the contract level:

```text
no duplicated deterministic procedure where a validated central skill owns it
+
no loss of explicit semantic/authority boundaries
+
fail-closed behavior at unresolved operating sources/gates
+
consumer initialization and actions resolve through exact pinned central skills
+
historical operating metrics are not required for live operation
```

Future changes should be evaluated through contract tests, negative/adversarial cases, consumer parity, and real repository behavior rather than a rule-application score.
