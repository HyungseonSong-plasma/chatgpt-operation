# Operating System Baseline — Calvin

- **Version name:** Calvin
- **Baseline date:** 2026-09-01
- **Repository:** `HyungseonSong-plasma/moose-test-repo`
- **Working ref at baseline:** `refactor/qpx-harness-generality`
- **Status:** first named Adaptive Rule Working Set baseline
- **Record type:** historical comparison snapshot; do not rewrite to match later behavior

## 1. Design objective

Calvin rejects the assumption that one universal simultaneously active rule set should cover every possible MOOSE/QPX situation.

Its operating objective is:

```text
minimum active rule load
subject to
acceptable decision, prevention, and closure quality for the current context
```

The system favors local decision quality, explicit routing, and rapid rule activation/unloading over global rule completeness.

## 2. Architecture

```text
moose-test-init
    -> BOOTSTRAP
    -> CORE
    -> current STATE
    -> Router
    -> primary PHASE PACK
    -> triggered auxiliary / temporary rules
    -> execution
    -> next user turn re-evaluates the working set
```

Primary phase packs:

```text
PLAN
RESEARCH
IMPLEMENT
VALIDATE
CLOSE
```

Auxiliary packs:

```text
MUTATE
SCIENTIFIC_EXECUTION
TEMPORARY DIAGNOSTIC MATERIAL
```

Dormant rules remain discoverable through the rule inventory rather than permanently occupying the active context.

## 3. Initial rule-load heuristic

These values are operating heuristics, not hard capability limits of the model:

```text
Core pack:                  5-8 material invariants
Primary phase pack:         5-10 material rules/contracts
Temporary diagnostic pack: 0-4 material rules/contracts
Typical active total:       12-20
Weighted review threshold:  ~25 load units
```

Weighted-load convention:

```text
simple invariant/direct gate                = 1
triggered rule with material judgment       = 2
branch-heavy rule with dependencies         = 3
```

Initial interpretation:

```text
<= 18 weighted units  -> GREEN
19-24                 -> YELLOW
>= 25                 -> RED / unload or refactor
```

These thresholds are provisional and should be replaced or refined by observed operating data.

## 4. Rule activation model

Every new user turn is a rule-set re-evaluation event.

Activation considers:

```text
current issue/state
current primary phase
immediate unresolved obligation
new user intent
new evidence or failure symptom
known incident signatures
```

The desired behavior is:

```text
relevant rule needed     -> activate
phase changes            -> unload old phase pack and load new one
symptom resolved         -> unload temporary diagnostic material
rule not currently needed -> leave dormant in inventory
```

A rule existing in the repository does not imply that it should be active in every chat context.

## 5. Canonicality hypothesis

Calvin distinguishes two forms of reusable operating knowledge:

```text
Canonical Rule
  -> what behavior/control is correct

Canonical Activation Pattern
  -> in what context that rule should be activated
```

An activation pattern should not be treated as canonical merely because one execution produced no error. Repeated evidence should support that the activation was:

```text
relevant
correct
non-interfering
repeatable
```

False activation and missed activation are both routing evidence.

## 6. Prevention and incident learning

Calvin inherits the prospective incident-learning model:

```text
NOVEL
KNOWN_BUT_NOT_ENFORCED
KNOWN_AND_GATE_BYPASSED
GATE_DEFECT
ENVIRONMENT_ESCAPE
UNRESOLVED
```

It additionally records whether the relevant phase/rule pack was active at the incident. This is intended to distinguish:

```text
RULE_ABSENT
RULE_EXISTS_BUT_NOT_LOADED
TRIGGER_OR_ROUTING_MISS
GATE_BYPASS
GATE_DEFECT
```

Known recurrence can trigger enforcement-promotion review rather than automatic rule accumulation.

## 7. Baseline evidence state

At Calvin baseline creation:

- the Adaptive Rule Working Set architecture is implemented in the repository operating documents;
- cross-chat bootstrap is available through `moose-test-init` and `BOOTSTRAP.md`;
- rule inventory and phase routing exist;
- incident learning includes activation-state evidence;
- the previously accumulated root-cause distribution exists as a historical baseline;
- no sufficient prospective dataset yet exists to claim that Calvin reduces incident rate or to establish an empirically optimal active-rule size.

Therefore Calvin begins as an **architectural baseline**, not as a proven performance improvement.

## 8. Metrics for later comparison

Future operating-system versions should compare against Calvin where measurement coverage permits:

```text
incident rate / bounded work item
known recurrence rate
pre-execution catch rate
gate-bypass rate
gate-defect rate
enforcement coverage
novel-class share
working-set miss rate
false activation rate
missed activation rate
active rule-load distribution by phase
error rate versus active weighted rule load
WCC / T-WCC / EVR / DBR / RWR / CLR / FBR
```

Useful phase-level comparisons include:

```text
PLAN      -> active load vs framing/clarification errors
RESEARCH  -> active load vs provenance/model errors
IMPLEMENT -> active load vs construction/rework errors
VALIDATE  -> active load vs false PASS/FAIL and runtime classification errors
CLOSE     -> active load vs closure/learning classification errors
```

## 9. Comparison guardrails

A later version should not be declared superior to Calvin from raw incident percentages alone.

Comparison should control or report, where possible:

```text
number of bounded work items
complexity mix (C1-C4)
phase/workload mix
classification coverage
model/version changes
repository/code changes that materially alter failure opportunities
measurement-window length
```

Prefer evidence of reduced known recurrence and routing/activation error without degraded closure quality.

## 10. Upgrade rule

When Calvin is materially superseded:

```text
1. preserve this file unchanged;
2. create a new dated named-version baseline;
3. record the architectural delta;
4. report comparable pre/post metrics;
5. identify which Calvin hypotheses were supported, rejected, or still unresolved.
```

This turns operating-system evolution itself into an empirical engineering process.
